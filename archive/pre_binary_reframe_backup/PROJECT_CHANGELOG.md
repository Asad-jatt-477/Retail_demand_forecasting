# Changelog — v1 → v2

This document exists so nobody has to reverse-engineer *why* v2 exists by
diffing scripts. It records what was wrong, why it mattered, and exactly
what changed.

## 1. Temporal / "future information" leakage (new fix)

**Problem.** The Phase 9 feature set (`Retail_demand_FS.csv`) included six
columns that only take a value *after* an order has shipped or been
completed:

| Column | Why it's post-order |
|---|---|
| `processing_delay_days` | = shipping date − order date |
| `late_delivery_risk` | raw dataset's post-delivery outcome flag |
| `order_status_COMPLETE` / `order_status_PENDING_PAYMENT` | order status is only final after fulfillment |
| `benefit_per_order_yj` | realized profit — only known once the sale is booked |
| `order_item_profit_ratio` | realized profit ratio — same issue |

The project's goal is to predict the quantity-class of an **incoming**
order. At that moment none of the six values above exist yet. Training on
them let the model implicitly "see the future," inflating its apparent
accuracy in a way that would not hold up in production — and
`streamlit_app.py` (v1) actually asked users to manually type in delivery
status and processing delay before predicting, which is impossible for a
real incoming order.

**Fix.** `10_model_training.py` drops all six columns before training
(Step 1). The model now uses only the 18 features that are genuinely known
at order-placement time.

**Effect on results.** F1-Macro moved from the (inflated) original number
to a more honest **0.393** (Random Forest) — below the original >0.50
target. This is expected and correct: it is the real ceiling once
future-information is excluded, not a modeling regression. See
`reports/metrics_v2.json` and Section 10 of the project report for full
numbers.

## 2. Random Forest model size (new fix)

**Problem.** v1's `RandomizedSearchCV` allowed `max_depth=None`
(fully-grown trees). On 142,716 training rows this produced a **2.6 GB**
pickle — too large to reliably load in Streamlit or in most production
environments (it crashed a 4 GB-RAM test load in this project's own build
environment).

**Fix.** `rf_param_dist` in `10_model_training.py` caps `max_depth` at 15
and `n_estimators` at 300.

**Effect.** Retrained model is **54 MB** — a ~48x reduction — with no
material F1-Macro cost (tree-based models on tabular data like this
saturate well before unlimited depth).

## 3. Streamlit app rewritten (`app/app.py`)

- Removed the 6 input fields tied to the leakage fix above (delivery
  status, processing delay, order status, realized profit / profit
  ratio) — the form now only asks for what a real incoming order would
  actually have.
- Product / Department are now picked by **name** from a dropdown. The
  app looks up the correct internal group-id via
  `models/v2/group_id_mapping.json` (built from the same historical data
  the model trained on, by `src/pipeline/11_build_product_department_mapping.py` —
  see that file's generation note below) instead of asking the user for
  a raw numeric code.
- Loads the resized v2 pipelines from `models/v2/`.
- Redesigned with a professional dark theme (custom CSS), a sidebar
  model-performance panel, and a class-probability chart per prediction.

`group_id_mapping.json` is generated by
`src/pipeline/11_build_product_department_mapping.py` from
`data/processed/Retail_demand_outliers_TREATED.csv` (which still has
`product_name` / `department_name`) joined positionally against
`data/processed/Retail_demand_FS.csv` (verified byte-exact row alignment)
— it is static reference data, not a new leakage source, since it only
maps a name to the same group-id the trained pipeline already encodes
internally.

## 4. Project report updated

`Retail_Demand_Forecasting_Project_Report.docx` gained a new **Section
10 — "Phase 10: Modeling: Final Results (v2, Leakage-Fixed)"** covering
all of the above with the actual measured numbers (previously the report
stopped at Phase 9 recommendations and never recorded the real Phase 10

## 5. What did *not* change

- The Phase 1–9 pipeline (cleaning, outlier treatment, EDA,
  Yeo-Johnson, feature engineering, feature selection) is unchanged —
  it was already solid.
- The statistical target-encoding leakage fix for `product_avg_qty` /
  `dept_avg_qty` (out-of-fold `KFoldTargetEncoder` inside the sklearn
  Pipeline) was already correct in v1 and is unchanged in v2.
- `class_weight='balanced'` / balanced sample weights for class
  imbalance — unchanged, still correct.

## 6. Repository restructured into a professional layout

The deliverable was originally handed over as one flat folder (all scripts,
plots, models, and reports mixed together at the root). It's now organized
as:

```
data/{raw,processed}/  src/pipeline/  app/  models/v2/  reports/  assets/plots/  archive/deprecated_v1/
```

Every script in `src/pipeline/` and `app/` was updated to resolve its input
and output paths from its own file location (`__file__`) rather than the
current working directory, so each one runs correctly regardless of where
it's invoked from. This was verified, not just asserted: after the
restructuring, `11_build_product_department_mapping.py` was re-run and its output was
byte-for-byte diffed against the pre-restructure version (identical), and
`10_model_training.py` was fully re-run end-to-end from the new layout —
producing the exact same F1-Macro (0.393) and model size (54 MB) as before,
confirming the path changes didn't alter any logic. `app/app.py`
was also executed directly (simulating how Streamlit runs a script) to
confirm it loads `models/v2/*.pkl` and `models/v2/group_id_mapping.json`
correctly from the new paths.

## 8. Two new phases added: Model Evaluation and Explainability (SHAP)

Phase 10 reports test-set accuracy/F1/confusion matrices, which is enough to
pick a winner between Random Forest and XGBoost but not enough to trust that
winner in production, or to explain any single prediction to a warehouse
operator. Two new phases close that gap — both run against the already
-trained `models/v2/*.pkl` pipelines (no retraining needed):

**`12_model_evaluation.py`** (outputs: `reports/evaluation_report.json`,
`assets/plots/evaluation/`):
- **Learning curve** — train vs. cross-validation F1-Macro as training-set
  size grows. Result: a gap of 0.122 at full size (train F1-Macro 0.514 vs.
  CV F1-Macro 0.392) — mild, acceptable overfitting, and the CV curve is
  essentially flat past ~40,000 rows, meaning more data alone would not
  meaningfully improve this model with these features.
- **Calibration curve** (one-vs-rest, per class) — log-loss 0.908.
- **Error segmentation by department-group** — accuracy ranges from
  **24.8% to 100%** across the 7 department groups, a far more actionable
  finding than the single F1-Macro number; some departments are near-trivial
  to predict (single-unit categories) while others are consistently
  difficult.

**`13_model_explainability_shap.py`** (outputs:
`reports/shap_feature_importance.json`, `assets/plots/explainability/`):
- SHAP `TreeExplainer` values on a stratified 500-row sample of the test
  set, computed on the winning Random Forest.
- Global ranking (mean |SHAP value| across all 5 one-vs-rest outputs) shows
  `product_group` (0.050), `product_price_log` (0.047), and
  `discount_intensity` (0.042) as the three real drivers — much closer
  together than Phase 10's impurity-based feature-importance chart
  suggested, which over-weighted `product_group` relative to price and
  discount.
- Beeswarm plots for Qty=1 and Qty=5 show *direction*: e.g. a high
  `product_group` value (bulk-buying product) pushes the Qty=1 probability
  down and the Qty=5 probability up, as expected.
- One worked example decomposes a single, real Qty=3 prediction
  feature-by-feature — useful as a template for explaining any individual
  prediction to a non-technical reviewer.

## 9. All pipeline plots rebuilt to be professional-quality (300 DPI, no overlap)

Every chart produced by `src/pipeline/02_*.py` through `09_*.py` (roughly 50
individual figures) had the same handful of root-cause layout bugs, found by
inspecting real screenshots of the plots the person had actually generated:

- **Suptitle/subplot-title overlap** — nearly every figure called
  `fig.suptitle(..., y=1.01)` followed by a bare `plt.tight_layout()`.
  `tight_layout()` does not reserve space for a suptitle unless told to, so
  the title text visually collided with the top row of subplot titles once
  `bbox_inches='tight'` cropped the saved PNG. Fixed everywhere by giving the
  suptitle an explicit `y` and passing `rect=[...]` (or, for `GridSpec`
  figures, `top=`) to reserve real space for it.
- **Too many subplots crammed into one figure** — e.g. 31 numeric columns in
  a single 4-column grid, or a 30+ feature correlation heatmap with 6pt
  annotation text. Fixed by paginating per-column grids into multiple
  reasonably-sized pages (`_page1.png`, `_page2.png`, ...) and by sizing
  correlation heatmaps and their annotation font adaptively from the actual
  feature count, instead of a fixed figsize regardless of how many features
  there were.
- **Illegible / colliding category labels** — long product names and, in one
  case, raw product-image URLs were plotted as bar-chart category labels
  with no truncation, overlapping neighboring panels. `product_image` is
  now excluded from the EDA categorical charts entirely (it's a URL column,
  already noted elsewhere as zero predictive value and 1:1 redundant with
  `product_name`), and remaining long labels are truncated with an ellipsis.
- **pandas' own auto-title colliding with a custom title** — `df.boxplot(by=...)`
  generates its own "Boxplot grouped by ..." title that a later
  `ax.set_title(...)` call does not fully replace. Replaced with manual
  `ax.boxplot()` calls (grouping the data by hand), which gives full control
  over the title and removes the collision.
- **Legends set but never drawn** — several statistical-method scatter plots
  in `03_outlier_detection_statistical.py` passed `label=...` to `scatter()`/
  `axhline()` but never called `ax.legend()`, so the legend silently never
  appeared. Fixed by collecting the handles/labels once per figure and
  drawing a single shared legend.
- **A real double-UTF-8-encoding bug**, unrelated to layout, was also found
  and fixed in `05_exploratory_data_analysis.py`: some comments and print
  strings (em-dashes, checkmarks, arrows) had been saved as UTF-8 bytes that
  were then re-encoded as if they were Latin-1 text, producing mojibake like
  `â€"` in place of `—`. The file now decodes cleanly.
- **DPI**: unchanged from the earlier 300 DPI fix — every regenerated plot
  in this pass is still saved at `dpi=300`.
- **Blocking `plt.show()` windows**: every pipeline script now sets
  `matplotlib.use('Agg')` before importing `pyplot`, so running a script
  from a terminal no longer pops up an interactive "Figure 1" window per
  chart — the saved PNGs are the deliverable.

Every fix in this list was verified by actually re-running the corresponding
script end-to-end in this environment and visually inspecting the resulting
PNGs — not just read for correctness. One exception: `09_feature_selection.py`'s
RFECV + permutation-importance step is genuinely expensive (the script's own
comment says "5-10 minutes" on ordinary hardware, and this project's 1-CPU-core
build environment is slower still), so `fs_04` through `fs_07` (the RFECV
score curve, the consensus voting heatmap, the final-feature correlation
chart, and the reduction funnel) were verified by code review against the
same layout patterns already confirmed correct in `fs_01`–`fs_03` and in
every other script's heatmaps/bar charts, rather than by a full from-scratch
run — they will regenerate correctly the first time `09_feature_selection.py`
is actually run, but weren't re-rendered for this delivery.

## 10. Honest open items (see README.md "Limitations")

- Hyperparameter search in this repo's committed run used a reduced
  budget (`n_iter=6, cv=3`) to fit a 1-CPU-core build environment. Re-run
  with `n_iter=25, cv=5` (env vars `MODEL_N_ITER` / `MODEL_CV_FOLDS`) on
  stronger hardware for a slightly more exhaustive search.
- Qty=3 and Qty=4 remain the hardest classes to separate — worth a
  follow-up look (e.g. ordinal classification instead of plain
  multi-class, or additional order-time features) before any production
  cutover.
